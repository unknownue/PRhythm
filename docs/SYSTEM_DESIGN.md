# PRhythm System Design

## 1. System Overview

PRhythm is a multi-agent architecture GitHub PR analysis system that automatically generates PR analysis reports through configurable analysis schemes.

### Core Features
- Multi-repository support: Independent configuration and workspace for each repository
- Configurable analysis schemes: Support for default and custom schemes
- Multi-agent collaboration: Stage-wise PR analysis workflow
- Condition matching: Automatic selection of appropriate analysis schemes based on PR characteristics
- Multi-format output: Support for Markdown, HTML, JSON, and other formats

## 2. Directory Structure Design

### 2.1 Configuration Hierarchy
```
config/
├── global.json              # Global configuration: API keys, system defaults
├── repositories/            # Repository-specific configurations
│   ├── {repo-name}.json         # Single repository config: trigger conditions, scheme selection
│   └── _template.json           # Template for new repository configuration
└── schemes/                 # Analysis scheme definitions
    ├── default/                 # Built-in system schemes
    └── custom/                  # Repository-specific custom schemes
```

**Configuration Priority:** Repository Config > Global Config > System Defaults

### 2.2 Runtime Workspace
```
workspaces/
└── {repo-name}/            # Independent workspace for each repository
    ├── metadata/               # Metadata: analysis history, repository info
    ├── repo-previous/          # Pre-merge code state
    ├── repo-merged/            # Post-merge code state
    ├── reports/                # Generated analysis reports
    └── temp/                   # Temporary files
```

**Lifecycle:** Dynamic Creation → Analysis Usage → Periodic Cleanup

### 2.3 Source Code Organization
```
src/
├── agents/                  # Agent implementation layer
├── core/                    # Core service layer
├── utils/                   # Utility function layer
└── models/                  # Data model layer
```

**Dependencies:** models ← core ← agents ← main.py

## 3. Agent Workflow

### 3.1 Agent Collaboration Model
```
GitHub PR Event
    ↓
Agent-1 (scheme_selector)
    ↓ Select analysis scheme
Agent-2 (pre_merge_collector) ←→ Agent-3 (post_merge_collector)
    ↓ Collect data                    ↓ Collect data
data_aggregator (Data aggregation)
    ↓ Build analysis prompt
LLM Service (Generate analysis report)
    ↓
Agent-4 (report_processor)
    ↓ Post-processing and formatting
Final Report
```

### 3.2 Agent Responsibilities

#### Agent-1: scheme_selector
- Analyze PR content (labels, file changes, descriptions, etc.)
- Select analysis scheme based on repository configuration condition rules
- Handle scheme fallback logic

#### Agent-2: pre_merge_collector
- Operate in repo-previous directory
- Checkout to commit before PR merge
- Collect pre-merge code environment data
- Execute pre-merge tasks defined by the scheme

#### Agent-3: post_merge_collector & data_aggregator
- Operate in repo-merged directory
- Checkout to commit after PR merge
- Collect post-merge code environment data
- Aggregate all data and build analysis prompt

#### Agent-4: report_processor
- Receive raw analysis report generated by LLM
- Execute post-processing tasks (link fixes, formatting, etc.)
- Generate final reports in multiple formats

## 5. Scheme Selection Mechanism

### 5.1 Condition Matching Logic
```
1. Read analysis.schemes.conditions from repository configuration
2. Sort by priority (high > medium > low)
3. Evaluate conditions one by one:
   - label_contains: PR labels contain specified value
   - files_changed: Number of changed files comparison
   - files_pattern: File path pattern matching
   - and/or: Compound condition logic
4. Use the first matching scheme
5. Use default scheme if no match
6. Use fallback scheme if scheme doesn't exist
```

### 5.2 Supported Condition Types
- **label_contains**: Check PR labels
- **files_changed**: Number of changed files
- **lines_changed**: Number of changed code lines
- **files_pattern**: File path matching
- **author**: PR author matching
- **branch**: Target branch matching
- **and/or**: Compound logical conditions

## 6. Workspace Management

### 6.1 Repository Setup

Use the setup script to create workspace structure for a new repository:

```bash
./scripts/setup_repo.sh https://github.com/user/example-repo
```

The script will:
1. Extract repository name from GitHub URL
2. Create complete workspace directory structure under `workspaces/{repo-name}/`
3. Initialize metadata files for tracking analysis history
4. Generate repository configuration template in `config/repositories/{repo-name}.json`
5. Clone the repository to both `repo-previous` and `repo-merged` directories

### 6.2 Workspace Structure

Each repository workspace contains:
- **metadata/**: Analysis history, repository info, last processed PR
- **repo-previous/**: Git repository clone for pre-merge state
- **repo-merged/**: Git repository clone for post-merge state  
- **reports/**: Generated analysis reports organized by year/month
- **temp/**: Temporary files during analysis

## 7. Extensibility Design

### 7.1 Adding New Analysis Schemes
1. Create scheme configuration file in config/schemes/ directory
2. Add corresponding prompt and report templates in templates/ directory
3. Reference new scheme in repository configuration

### 7.2 Adding New Agents
1. Implement new Agent by inheriting BaseAgent class
2. Register Agent in analysis_engine.py
3. Add Agent task definitions in scheme configuration

### 7.3 Extending Condition Matching
1. Add new condition type handling in config_manager.py
2. Implement condition evaluation logic in scheme_selector.py
3. Update configuration templates and documentation

## 8. Deployment and Maintenance

### 8.1 System Requirements
- Python 3.8+
- Git 2.0+
- Sufficient disk space to store multiple repository copies

### 8.2 Monitoring Points
- GitHub API quota usage
- LLM service call count and cost
- Workspace disk usage
- Analysis task execution time and success rate

### 8.3 Maintenance Tasks
- Periodically clean up expired workspace files
- Monitor and rotate log files
- Update analysis schemes and templates
- Backup important configuration and report data
